# Hands-free "Hey Claude" dictation into the terminal (WhisperWriter wake word)

## Context
Neill wants to talk to Claude Code hands-free: say a wake phrase, speak, and the text lands in the
terminal, with no Pause-key press. He wants it to work with his AirPods. Decisions he made:
- **Mic: toggle between laptop and AirPods** (tray switch). Holding the AirPods mic open puts them in
  Bluetooth hands-free mode, so audio sounds like a phone call while the listener is on. The toggle
  includes **Off**, which closes the AirPods mic and brings audio quality back.
- **Scope: terminal only.** The wake word only fires when Windows Terminal is the foreground window.

Current state (verified 2026-10-16): the live install is `C:\Tools\whisper-writer`. Its origin is
upstream savbell, and the GPU fixes sit there uncommitted. The maintained copy is the public fork
`github.com/neillgroom/whisper-writer-gpu`. In `config.yaml`: `activation_key: pause`,
`recording_mode: hold_to_record`, `sound_device: null`, `sample_rate: 16000`. `ResultThread._record_audio`
(`src/result_thread.py:119`) already runs WebRTC VAD stop-on-silence (900 ms) when the mode is
`voice_activity_detection`. It reads the mode from global config each time it records.

`origin/main` (12bbe00) matches the live install's `src/main.py` and `src/result_thread.py`, apart
from line endings. `main` has no `tests/` directory yet.

Two draft PRs from July (#1 and #2, "Helene" voice commands) sit unmerged on
`agent/windows-voice-control`. That branch adds a spoken-prefix command router: a transcript that starts
with "Helene" goes to a broker that launches apps and CLIs. This plan does not build on that branch or

**Safety invariant:** the wake path is dictation-only. If #2 ever lands, wake-triggered transcripts must
never route to the command broker, because an always-on mic must not be able to launch anything.

The six `pythonw` processes are one chain: `run.py` → `src/main.py` → `transcription_worker.py`.
Each step is a venv redirector (`venv\Scripts\pythonw.exe`) plus its base Python 3.11 child. An earlier

## Chunk 1: wake listener → dictation, laptop mic, terminal gate

**Threading rule: all app state changes happen on the Qt main thread.**
- `KeyListener` callbacks fire on the pynput hook thread. A new `QObject` bridge re-emits
  `on_activate`/`on_deactivate` as Qt signals (queued connection). `main.py` therefore handles key
  events on the main thread and never blocks the low-level keyboard hook (7048f52d53dc).
- The wake listener emits `wakeSignal` across threads the same way. Every read and write of
  `recording_source` happens on the main thread, so there is no lock to get wrong.

**The mic stream stays open; there is no pause/resume handoff.**
- New `src/wake_listener.py`: a `QThread` that keeps one `sd.InputStream` open for as long as wake is
  enabled, runs openWakeWord, and emits `wakeSignal(score)`. It never closes for a recording. Windows
  shared-mode capture allows a second stream on the same device, and Chunk 0 proves that on both mics.
- `main.py` handles `on_wake` on the main thread. **It drops any wake that arrives while a recording
  is running or a transcript is being typed**, which covers queued or duplicate signals and the
  listener hearing your own dictation (53ed11a9ad4a, c118159c4288, 93f4c8efe5b4, 6931a972d1d8 are
  closed by deleting the handoff).
- If the stream errors, the listener stops, shows a tray error, and stays stopped. It does not retry
  in a loop.

**Wake recordings always end on their own.**
- `ResultThread.__init__(local_model, source='key'|'wake', device=None)`. For `source='wake'`:
  - the mode is `voice_activity_detection`, whatever the global `recording_mode` says;
  - a **no-speech deadline** (`wake_options.no_speech_timeout_ms`, default 4000) ends the recording with
    no output;
  - a **hard cap** (`wake_options.max_recording_s`, default 60) ends it regardless.
- The capture loop waits with `data_ready.wait(timeout=0.25)` and checks both deadlines against the
  wall clock every pass, so a stalled callback (a Bluetooth drop) still ends the recording
  (cb6fb7fc24d8).
- Pause-key recordings keep their current `hold_to_record` behavior and do not use the new deadlines.
- `on_activation` and `on_deactivation` are ignored while a wake recording runs, and a wake is
  ignored while a key recording runs (81558eb7d011).

**The terminal gate holds through the last keystroke.**
- New `src/foreground.py`:
  - `foreground_window()` → HWND.
  - `process_name(hwnd)` → `GetWindowThreadProcessId` → `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)`
    → `QueryFullProcessImageNameW` → basename, closing the handle in `finally`.
  - **Fail closed:** anything null or failed returns `None`, and `None` is never allowed.
- On wake: record the foreground HWND and check its process against `wake_options.allowed_processes`.
  No match → nothing happens.
- Typing: `InputSimulator.typewrite(text, should_continue=None)` gets an optional predicate, checked
  before **every** character. The wake path passes "the foreground HWND is still the recorded one".
  The first failed check stops typing, and the untyped remainder goes to a tray notification
  (ef7f95cdc47f, 79534a0cb5ed). The key path passes nothing, so its behavior is unchanged.
- `StatusWindow` gets `Qt.WA_ShowWithoutActivating` and `Qt.WindowDoesNotAcceptFocus`, so showing it
  can never take focus from the terminal (c15ff1a2656e).
- A wake transcript that is empty after `strip()` is dropped. That applies before
  `add_trailing_space`, so a lone space is never typed or notified (693cf558edc7).
- Text is **typed only and never auto-submitted**. Neill presses Enter.

**Config and settings window.**
- `config_schema.yaml` gets a new `wake_options` section using only types the settings window already
  renders:
  - `enabled` (bool)
  - `wake_model` (str; not `model_path`, which the settings window special-cases)
  - `threshold` (float)
  - `allowed_processes` (str, comma-separated, default `WindowsTerminal.exe`)
  - `device` (str+options `laptop|airpods|off`)
  - `laptop_match` (str, default `Microphone Array`)
  - `airpods_match` (str, default `AirPods`)
  - `no_speech_timeout_ms` (int)
  - `max_recording_s` (int)
- `SettingsWindow`:
  - reloads its widgets from `ConfigManager` every time it opens, so a save never writes back a stale
    tray choice;
  - `get_config_value` uses `is not None`, so a `false` boolean is not replaced by the default
    (24a0cf5c6db6).
- New pins go into `requirements.txt` and `requirements-cpu.txt`: `openwakeword==0.6.0` and its
  resolved dependencies, exactly. A unittest asserts that `numpy` major < 2 and that `openwakeword`
  imports (4b5fcf4ed35a: pins land here, not in Chunk 0).

**Tests (unittest).**
- Foreground: allowed, denied, null HWND, `OpenProcess` failure → denied.
- `typewrite` with a predicate: a focus change after N characters stops the typing and hands back the
  remainder.
- `ResultThread` `source='wake'`:
  - silence ends at the no-speech deadline with no result;
  - constant speech ends at the hard cap;
  - a stalled callback still ends by the deadline.
- Main-thread state: a wake during a recording is dropped; a Pause press/release during a wake
  recording is ignored; an empty transcript is not typed.
- Settings window: a `false` boolean survives a save; a tray-set device survives open-then-save.
- Wake detector on WAV fixtures: one wake clip, one negative clip; only the wake clip fires.

## Chunk 2: tray mic toggle (Laptop / AirPods / Off)
- Tray submenu "Mic: Laptop | AirPods | Wake off". The choice persists to `wake_options.device`.
- **One mic choice for both paths:**
  - Laptop: the wake listener and Pause dictation use the input matched by `laptop_match`. This is a
    named device, **not** the Windows default, which can silently become the AirPods when they connect
    (b1870ed74035).
  - AirPods: both paths use the input matched by `airpods_match`.
  - Off: the wake stream is closed (AirPods leave hands-free mode) and Pause dictation uses the system
    default input, exactly as today.
- Resolver:
  - From `sd.query_devices()`, keep WASAPI-host-API entries with `max_input_channels > 0` and match
    the substring case-insensitively.
  - Zero matches → `None`. More than one → the lowest index, logged so the choice is visible.
  - Every stream opens with `WasapiSettings(auto_convert=True)` at 16 kHz mono int16, so the device's
    native format doesn't matter (702f92fb424f).
  - It never matches by index.
  - Observed 2026-10-16 with the AirPods paired but not streaming: only WDM-KS lists them, as
    `Headset (... Hands-Free ...;(AirPods Pro - Find My))`, and WASAPI lists nothing. WASAPI exposes
    the hands-free input only while it is connected. So "not found" is the normal disconnected state,
    and Chunk 0 records the exact WASAPI name while they are connected.
- AirPods chosen but not found:
  - The **stored choice stays `airpods`**. The effective state for this run is Off, with a tray
    notification.
  - Choosing AirPods in the tray again, or restarting the app, retries (6bcad5216271).
  - It never falls back silently to another mic.
- Tests:
  - resolver against a recorded `query_devices()` fixture: output-only entries are ignored, only WASAPI
    entries match, multiple matches resolve to the lowest index, missing → `None`;
  - toggle: sets the device for both paths, and a missing AirPods keeps the stored choice.
